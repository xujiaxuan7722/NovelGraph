## 1. 项目目标

**表层目标（课程原题）**：从《红楼梦》原文构建人物关系知识图谱，并提供问答。
**深层目标（现阶段定位）**：做一个**面向长文本的关系抽取与图谱构建框架**，以《红楼梦》验证、以《三国演义》做迁移验证。代码里不允许出现任何具体文本的知识；换书只换 schema 配置文件。

两个目标的关系：红楼梦是框架的测试集，不是终点。

## 3. v1 线：当前可运行的系统

### 3.1 流水线

```
原文(87万字) → 切315段 → GLM抽取(三元组+证据) → 证据校验(必须是原文子串)
```

**分层评估**：文本抽取层 F1 31.1%（P 34.0%）；模型知识层 F1 13.4%（P 18.5%）——**模型"记得"不如"读得"准**，是一条实证发现。

**QA 端到端（30 题，严格口径）**：完整系统 100%；去掉手工预定义仅靠 LLM+规则 66.7%（原作业该口径接近 0）。

**分关系召回**：主仆/家族/祖母/母子等文本直接陈述的关系召回较好；**堂亲 0/18、表亲 0/14、父女 0/8**——原文从不直说，属推理型关系，是抽取法的结构性上限（v2 用推导规则解决）。

### 3.5 v1 的已知问题

1. 候选源头质量受限：GLM-flash 激活参数仅 3B，切段 3500 字无跨段记忆，称谓消歧靠手工别名表；
2. 残留错误：如"贾宝玉的丫鬟"里仍混入平儿/紫鹃（别人的丫鬟）、"黛玉住在哪里"含怡红院（到访误判居住）；
3. 60% 图谱是共现噪声；
4. 实体集合封闭（手工 61 人表），不可迁移；
5. 曾因并行进程未杀干净导致 110 段重复记录（已在聚合层按段去重修复）；
6. 约 4.5% 段落未覆盖（7 段多次失败、1 段被智谱内容审查拦截、3 段未触达）。

## 4. v2 线：`kgx/` 框架（代码完成，待配额）

### 4.1 设计原则

- **schema 驱动**：实体类型、关系定义/方向/对称/functional 约束、易混判据、推导规则全部在 `schemas/<书>.yaml`，代码零领域知识；
- **单模型**：Gemini 3.7 Flash（用户指定）承担预扫描分类、抽取、别名归并、复核全部环节；
- **实体完全开放**：不给白名单，模型读到谁登记谁，别名由模型在阅读中读出；
- **证据一等公民**：每条关系必须有原文证据且同时提到双方，否则程序回原文检索补证，补不到即丢；
- **分层来源**：文本抽取 / 模型知识（复核时模型补充，无证据）/ 推导（规则，带推导链）分别标注、分别评估；
- **免费配额友好**：每次调用吃 3 回（约 2.3 万字），所有调用磁盘缓存，断点续跑，配额用尽自动退出次日续。

### 4.2 模块与借鉴来源

| 模块 | 文件 | 借鉴 |
|---|---|---|
| schema 加载 | `kgx/schema.py` | OneKE / Graphiti 的声明式本体 |
| Gemini 客户端 | `kgx/llm.py` | 速率/配额控制、503/429 分类退避、缓存、responseSchema 结构化输出 |
| 切分打包 | `kgx/chunking.py` | 按章节正则切、保留回号与偏移 |
| 实体预扫描 | `kgx/prescan.py` | **AI-Reader-V2** 六路候选（jieba 词性/n-gram/对话归属/标题/命名模式）+ 一次 LLM 分类别名分组 |
| 滚动登记簿 | `kgx/registry.py` | AI-Reader-V2 结构化清单上下文 + 增量更新 + 全文 grounding |
| 通读抽取 | `kgx/extract.py` | kg-gen 过程式 prompt、关系端点必须来自登记簿；**GraphRAG gleaning** 补抽一轮 |
| 程序校验 | `kgx/validate.py` | 证据定位（精确→模糊）、双方提及（含别名）、类型约束、回段检索补证 |
| 别名归并 | `kgx/resolve.py` | kg-gen entity_clusters 思路（一次 LLM 给全部合并组）+ 同类型约束 |
| 聚合 | `kgx/aggregate.py` | 方向规范化、计票、证据择优、functional 冲突 |
| 全局复核 | `kgx/review.py` | OneKE Reflection：分组推理裁决 + 模型知识补充 |
| 推理补全 | `kgx/infer.py` | schema 规则前向推理（同父→兄妹、父之父→祖父、父辈兄弟→堂亲…），带推导链 |
| 评估/导出 | `kgx/evaluate.py`、`kgx/export.py` | 金标准 P/R/F1 分层 + 人工抽检样本；导出面板兼容 JSON |
| 入口 | `kgx/cli.py` | `python -m kgx.cli run --schema schemas/hongloumeng.yaml --text data/hongloumeng11.txt --out runs/xxx [--chapters 1-10] [--gold gold.hongloumeng]` |

### 4.3 离线自测结果（已通过）

- 推理引擎：玩具家谱上正确推出兄妹/祖母/外祖父/堂亲，并正确抑制"已是堂亲者不再记表亲"；
- 校验器：证据不在原文 → 自动回检索补证；类型不符正确拒绝；
- 聚合：对称关系合并计票、functional 冲突按票数裁决；
- 切分：120 回、44 个打包块（最大 2.4 万字）；预扫描 Phase 1 全书 400 候选、30 秒。

### 4.4 真实试跑暴露并已修复的问题

- 503 高负载频繁 → 退避加长（最多 10 次，15→120s）；
- 补抽失败曾导致第一遍结果整体丢失 → 补抽失败改为非致命；
- 每日配额耗尽 → 抛 `QuotaExhausted`，保存登记簿与进度退出。

### 4.5 Gemini 免费配额阻塞（08-21 → 08-31 已解决：改用商汤 Token Plan）

- 实测 `gemini-3.7-flash` 免费档 **每天 20 次请求**（429 `GenerateRequestsPerDayPerProjectPerModel-FreeTier, limit: 20`）；全书约 130 次调用 → 需一周；08-21 至 08-31 停摆。
- 08-31 决定改用商汤 Token Plan 免费网关（`token.sensenova.cn/v1`，OpenAI 兼容），主模型 `deepseek-v4-flash`；积分 60,000/5h、600,000/周，全书预算约 9,300 积分，积分不是约束。Gemini 类保留作备用 provider。
- 09-01 接入完成（`kgx/llm.py` `OpenAICompat`、`--provider`），1–3 回与 4–6 回各跑通一遍；数据与问题记录在 `docs/待办-2026-09-01.md`。

### 4.6 商汤网关实测（09-01）

- **思考必须关**：默认思考会把 `max_tokens=16000` 全烧在 reasoning、正文为空；`reasoning_effort:"none"` 有效，`"low"` 无效。抽取阶段关思考，复核阶段可用 `--review-thinking` 开。
- **单块对照（第 1–3 回，同一登记簿）**：DeepSeek 57s、19.3k 入 / 6.7k 出，64 关系 / 45 新实体，校验通过 39；Gemini 3.7 Flash 47 关系 / 15 新实体，校验通过 24；三元组重合 34。DeepSeek 抽得更多也更"脏"（证据逐字命中 69% vs 85%）。
- **`inference tpm exhausted` 429**：出现时机与本方用量不成函数关系（闲置 90s 后 6k 小请求也撞；大请求后需等 3–4 分钟），判断为公测共享池瞬时容量限制。处理：按 token 节流避免连发 + 45s×n 退避重试，不退出。1–3 回 5 次调用 355s，其中约 3 分钟在等 429。
- **校验漏斗（1–3 回）**：抽取 102 → 通过 30。丢弃 72 = 无合格证据 44（多为主语省略/别名未登记的真关系，如"林如海 父女 黛玉｜今只有嫡妻贾氏，生得一女，乳名黛玉"）+ 类型不符 19（全是"贾府 家族 贾母"方向反了，可程序翻转）+ 实体未登记 9。
- 修复 `registry.merge` 的 `[drop] | set` TypeError（首次归并出组即崩，Gemini 时期从未触发）。
- **09-01 全书跑完**：F1 35.8%（P28.8/R47.5，+推导层），文本层 26.9%；漏斗 2,767→1,901→612→246→303；过程中修的 7 类问题与下一步见 `docs/待办-2026-09-01.md` §6。
